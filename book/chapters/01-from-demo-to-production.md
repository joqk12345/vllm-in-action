# 第 1 章 从能跑到能上线

<!-- verified: fe1c317157d4478fdc0e02096447e61305b871e9, 2026-08-16 -->

本书研究的不是“怎样执行一条 `vllm serve`”，而是怎样把 token 稳定、经济地交给用户。能返回文本只证明功能路径畅通；能上线还要求在输入长度、并发和故障发生变化时，延迟、正确性与成本仍落在边界内。

## 1.1 一条请求其实是两种计算

生成分为 prefill 与 decode。prefill 一次处理提示词，矩阵通常较大，容易利用 GPU 计算能力；decode 每步只增加少量 token，却反复读取权重与历史状态，常受内存带宽和调度开销限制。因此“每秒 token”必须拆成：

- 首 token 延迟（TTFT）：排队、输入处理和 prefill 的总结果；
- token 间延迟（ITL）：连续输出的节奏；
- 端到端延迟（E2E）：TTFT 加全部 decode；
- goodput：同时满足 TTFT/ITL SLO 的请求速率，而非只看毛吞吐。

平均输入 128 token 的聊天基线，不能外推到 64K 文档问答。离线批处理也不应为流式 ITL 牺牲批量效率。第一原则是先描述工作负载，再谈参数。

## 1.2 vLLM 优化了什么

传统静态批处理把序列绑在一起，短请求会等待长请求，KV cache 又容易因连续预留造成内部与外部碎片。vLLM 的核心解法是把请求变成连续到达、连续离开的 token 工作集：调度器按 token 预算组成批次；KV cache 按块分配；model runner 把逻辑批次变成设备张量；注意力后端按平台和模型能力执行。

这不是“PagedAttention 单点魔法”。生产收益来自控制面和数据面的组合：连续批处理提高设备占用，分页缓存提高可容纳序列数，prefix caching 避免重复 prefill，chunked prefill 限制大提示词独占一个迭代，CUDA Graph/编译和融合算子降低执行开销。

## 1.3 从约束反推设计

上线前写一页服务契约：模型与任务、输入/输出长度分布、到达过程、并发、TTFT/ITL 分位数、可接受失败率、硬件拓扑和成本上限。之后依次回答：

1. 权重能否以目标精度装入？
2. 剩余显存能放多少 KV 状态？
3. 单副本在哪个并发点开始排队？
4. TP/PP/DP/EP 引入的通信是否值得？
5. 前缀复用、推测解码或量化是否命中真实瓶颈？
6. 过载时拒绝、排队还是降级？

不要同时打开五个优化开关。固定模型 revision、镜像、驱动和 workload，逐项实验；否则结果不可归因。

## 1.4 一张系统地图

```text
client -> API/renderer/tokenizer -> EngineCore/Scheduler
       -> Executor -> Worker -> ModelRunner -> model/kernels
       <- detokenizer/streaming  <- sampled token
```

V1 默认是多进程结构。API 进程处理协议和输入，EngineCore 持有调度与 KV 控制状态，每个 accelerator 通常对应 worker。数据并行时还有 rank 间协调。边界的意义是故障域不同：HTTP 慢不必等同于 GPU 慢，tokenizer 饱和也不是注意力算子问题。

## 1.5 本书的使用方法

第 2—4 章建立指标、请求生命周期和 KV 心智模型；第 5—8 章完成可复现服务与分布式拓扑；第 9—12 章研究 benchmark、调度、热点注意力和算子；第 13—16 章把优化放进生产闭环。

每次调优都留下四件东西：假设、唯一变量、原始数据、回退条件。一个可靠结论的形式不是“打开 X 更快”，而是“在固定版本、模型、硬件与分布下，X 改善哪个分位数，代价是什么，在哪个边界失效”。

> **检查点**：若你不能画出请求从 socket 到 kernel 再返回 token 的路径，就先不要复制所谓最佳参数。
